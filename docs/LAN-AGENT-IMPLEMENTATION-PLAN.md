# Fylo Local Agent Implementation Plan

## Phase A source findings

Implementation status: Phases B through G are now implemented on the working
branch. The source findings below preserve the pre-change evidence used to
make the migration decisions; current behavior is documented in
`LAN-AGENT.md`.

This plan is based on direct source inspection of `p2p.App`,
`FileController`, `p2p.device`, `p2p.lan`, `p2p.transfer`,
`p2p.protocol`, the current Next.js Nearby/Transfers components, Maven,
Docker, and the LAN docs.

## Current Architecture

The current runtime is one Java process per device. `p2p.App` constructs
`FileController`, and `FileController` is the composition root for:

- HTTP gateway routes: `/upload`, `/download/{port}`, `/lan/*`, `/transfers`
- platform API routes: `/api/v1/*`, `/s/{slug}`, `/health`, `/metrics`
- WebSocket events on API port + 1
- mDNS discovery, device registry, presence heartbeats, LAN offers, pairing,
  active shares, and transfer queue
- optional cloud-shaped services: auth, users, PostgreSQL, Redis, MinIO/S3

The Local Agent boundary does not yet exist as a first-class package. The
right first move is to wrap the existing working implementation in a narrow
agent lifecycle/API boundary, then split cloud and local processes later.

## Current LAN Flow

`DeviceDiscoveryService` starts from `FileController.start()` on a virtual
thread. It creates JmDNS, registers the local service, listens for peer
services, resolves TXT records and IPv4 address, then calls
`DeviceRegistry.upsertOnline(...)`. `DevicePresenceManager` sweeps every 10
seconds and uses `HeartbeatService` to call peer `GET /lan/ping`; two missed
heartbeats mark an online peer offline.

The browser does not perform mDNS, UDP, raw TCP, or peer HTTP. It polls the
local Java process through Next rewrites:

- `GET /api/lan/devices`
- `POST /api/lan/connect`
- `POST /api/lan/send`
- `GET /api/lan/offers`
- `POST /api/lan/offers/{id}`
- `GET /api/transfers`
- `POST /api/transfers/{id}`

## Current Transfer Flow

The data path is already the desired one. The browser uploads a selected file
to the local Java process, which creates a `FileSender` on a dynamic high TCP
port and returns the share port/token. LAN send wraps those active shares in
an `OfferRequest`; the receiver accepts and uses `TransferManager` plus
`FileReceiver`/`PeerClient` to pull bytes directly from the sender's
`FileSender`. PeerLink framing, resume, SHA-256 verification, CRC32C repair,
queueing, and cancellation remain in `p2p.transfer` and `p2p.protocol`.

## Current Ports

- `7000`: actual Java default in `App` and Next default target today.
- `9090`: stale default in README, OpenAPI, Docker, Kubernetes, and manual
  connect fallback.
- `9091`: stale WebSocket example for the previous `9090 + 1` contract.
- `49152-65535`: dynamic `FileSender` ports generated by `UploadUtils`.
- WebSocket events are always API port + 1.

Phase B will establish `7000` as the Local Agent API/control default and keep
dynamic PeerLink ports documented instead of changing the data plane.

## Current mDNS Service

Source currently registers `_air._tcp.local.` while `docs/LAN-MODE.md`
describes `_peerlink._tcp.local.`. TXT records are:

- `id`
- `name`
- `os`
- `type`
- `version`
- `capabilities`

Phase E will choose `_fylo._tcp.local.` as the authoritative Fylo Local Agent
service name. This is a compatibility break for older `_air` or `_peerlink`
builds on the same LAN, acceptable for this pre-packaged agent phase and
documented as such.

## Agent-Owned Classes

These should be treated as local-machine responsibilities in this phase:

- `DeviceDiscoveryService`, `DevicePresenceManager`, `HeartbeatService`
- `DeviceIdentity`, `DeviceRegistry`
- `QrPairingService`, `TrustedDeviceService`
- `ControlPlaneClient`, `LanMessages`, `LanShareService`, `OfferManager`
- `FileSharer`, `FileSender`, `FileReceiver`, `PeerClient`, `TransferManager`
- `PeerLinkProtocol`, `TransferManifest`, `ResumeState`, `ProgressTracker`

## Cloud/Server-Side Classes

These remain cloud/backend responsibilities and should not be pulled deeper
into the agent in this phase:

- `AuthService`, `JwtService`, `SessionService`
- `UserService`, `PresenceService`, notifications, username sharing
- `PlanService`, link sharing, transfer history
- PostgreSQL repositories
- S3/MinIO/cloud object storage providers
- future cloud signaling and fallback transfer

## Required Changes

1. Add `p2p.agent.AgentConfig` to centralize agent host, port, WebSocket port,
   data/download directories, mDNS service type, and dynamic PeerLink range.
2. Add `p2p.agent.FyloLocalAgent` as the lifecycle entry point and keep
   `p2p.App` as a compatibility shim.
3. Add `p2p.agent.AgentServer` as a loopback-only `/agent/*` facade mounted
   by the current `FileController`.
4. Preserve `/lan/*` as the device-to-device LAN control plane for this phase.
5. Update the Next.js Nearby, incoming-offers, and transfers surfaces to call
   `/api/agent/*` through a `FYLO_AGENT_URL` rewrite that defaults to
   `http://127.0.0.1:7000`.
6. Replace `9090` fallback usage for manual LAN connect with the centralized
   `7000` agent default.
7. Rename the mDNS service type to `_fylo._tcp.local.` and update docs/tests.
8. Add structured lifecycle/control/transfer logs without logging bearer
   tokens, pairing secrets, JWTs, private keys, passwords, or file contents.
9. Create `docs/LAN-AGENT.md` and update existing LAN/protocol/architecture
   docs so the agent, port, and service-name contracts are consistent.

## Potential Breaking Changes

- mDNS service discovery changes from `_air._tcp.local.` to
  `_fylo._tcp.local.`. Mixed old/new builds will not auto-discover each other;
  manual connect remains available.
- Next.js Nearby routes move from `/api/lan/*` to `/api/agent/*`.
- The documented local default changes from stale `9090` references to `7000`.
- The first phase still uses the existing shared HTTP listener internally:
  `/agent/*` is loopback-guarded, while `/lan/*` remains reachable to peers.
  A later phase should split loopback UI API and LAN control listeners.

## Testing Plan

Automated:

- Compile with Maven.
- Run `mvn -q -Dtest=LanModeIntegrationTest test`.
- Run agent API focused tests for status, devices, send, offer approval, and
  transfer snapshots through `/agent/*`.
- Run the full `mvn test` suite where local infrastructure permits.
- Build the Next.js UI.

Manual two-device LAN test:

1. Run the Fylo Local Agent and Next.js UI on Laptop A and Laptop B.
2. Verify A discovers B and B discovers A over `_fylo._tcp.local.`.
3. Send a real file from A to B through Nearby.
4. Verify received file size and SHA-256.
5. Stop B's agent and verify A marks B offline after missed heartbeats.
6. Restart B and verify it appears online again.
7. Repeat with cancellation, large files, duplicate discovery, and manual
   connect fallback.
