PHASE B — WEBSOCKET REAL-TIME (Backbone §6.4)
════════════════════════════════════════════════════════════════

The backbone §6.4 specifies two WebSocket event types:
  TRANSFER_PROGRESS — sent during active transfers
  TRANSFER_STATUS   — sent on state change (COMPLETED, FAILED, PAUSED)

Additionally for Mode 3 (Username Share):
  TRANSFER_REQUEST  — notifies receiver of incoming request
  REQUEST_ACCEPTED  — notifies sender their request was accepted
  REQUEST_REJECTED  — notifies sender their request was rejected

B.1  Create: src/main/java/p2p/ws/WebSocketServer.java

     Use Java built-in com.sun.net.httpserver (already in use) with
     WebSocket upgrade handling, OR use a lightweight WebSocket library.

     Since the project uses plain HttpServer, implement WebSocket over
     the existing server using RFC 6455 handshake + framing:

     Endpoint: ws://host:9090/ws/events

     Authentication: token passed as query param
       ws://host:9090/ws/events?token=<accessToken>
       On connect: validate JWT, extract userId, register connection

     Connection registry:
       ConcurrentHashMap<String, WebSocketConnection> connections

## Security

  before any metadata is revealed
- Path traversal protection on filenames in both directions
- Range and checksum requests are bounds-checked
- Not yet included (recommended for hostile networks): TLS, token expiry,
  rate limiting — see the security section of

====
1. **Engine facade** — `p2p.engine.TransferEngine` + sealed `TransferSource` + `ShareCodes`; `FileController` composition switched to it. Existing `transfer/*` classes untouched (they are the engine internals).
2. **Storage seam** — `StorageProvider` + `LocalStorageProvider` (streams, hashes, sidecar metadata).
3. **Auth layer** — `JwtService` (HS256, persisted secret), `PasswordHasher` (PBKDF2), `SessionService` (rotation + replay revocation), `AuthService`.
4. **User system** — `User(Repository)`, `UserService`, `PresenceService`, `NotificationService`, `TransferHistoryService`.
5. **Mode services** — `DirectShareService` (codes/QR added to the existing upload response — backward compatible), mode 2 = existing `lan` package, `UsernameShareService`, `LinkShareService` (2-day default expiry, sweeper).
6. **Discovery extensions** — `QrPairingService` (one-time secrets → mutual trust), `TrustedDeviceService` (trust policy front).
7. **Unified API** — `ApiRouter` mounted on the same server; legacy routes unchanged so the current UI keeps working.
8. **Dedup** — multipart streaming unified in `MultipartUploads`.

### Phase 2 — hardening (next)
- `UserRepository` → PostgreSQL (JDBC/Hikari); `links.json`, history, sessions → tables. Schema already sketched in `FYLO_PROJECT_BACKBONE.md` §5.
- `StorageProvider` → MinIO/S3 implementation (multipart PUT, presigned GET for `/s/{slug}` offload).

Good question — the plan machinery is already built; what's missing is only the payment trigger. Let me walk through the three parts.

1. How free vs. paid is differentiated today
There is exactly one authority: PlanService.java. Every feature gate asks it at request time:


request → LinkShareService.enforceCreate()
              → plans.entitlementsFor(userId)
                    → subscriptions.json has an active entry?  → Entitlements.premium(storageBytes)
                    → otherwise                                → Entitlements.FREE
FREE: 10 GB files/storage, 10 links, 2-day expiry, no passwords/limits/analytics/revocation.
PREMIUM: 200 GB files, 500 GB–2 TB storage, unlimited links, 7/30/90/never expiry, all premium features.
Three places reflect the tier, and it's important to know which one enforces:

Where	Role
PlanService.entitlementsFor()	The enforcement — checked live on every action; changes take effect instantly, no re-login needed
GET /api/v1/plan	What the UI reads (tier + entitlements + usage) — this is how the frontend should show/hide premium controls
JWT plan claim	Informational only, stamped at login/refresh — never use it to enforce anything
2. How to switch a user to paid manually (today, for testing)
The seam already exists: PlanService.grantPremium(userId, storageBytes, expiresAtEpochMs) / revokePremium(userId). Without code, edit subscriptions.json in the data dir and restart:


[ { "userId": "<the user's uuid>", "storageBytes": 536870912000, "expiresAtEpochMs": 0 } ]
(0 = never expires; storageBytes picks the tier: 500 GB / 1 TB / 2 TB.) Get the uuid from users.json or /api/v1/users/me. This is exactly what the verification smoke tests did.

A nicer dev/admin option I can add in a few minutes: POST /api/v1/admin/grant-premium guarded by an ADMIN_TOKEN env var — flips a user live without restart.

3. Adding a payment gateway
Since you're in India: Razorpay for Indian customers (UPI/cards/netbanking), Stripe if you want global reach — the integration shape is identical, so the code below works for either. The key architectural rule: the gateway never talks to your entitlements directly — its webhook calls the existing grantPremium/revokePremium. You already built the hard part.


UI "Upgrade"                    Fylo backend                       Gateway
     │  POST /api/v1/billing/checkout {tier}                          │
     │──────────────►│                                                │
     │               │  create subscription/checkout (secret key,     │
     │               │  notes: {userId})  ────────────────────────────►
     │               │◄──────────────  checkout URL / order id        │
     │◄── redirect ──│                                                │

     │               │  payment/subscription activated →              │
     │               │    planService.grantPremium(userId, bytes,     │
     │               │                     currentPeriodEnd)          │
     │               │  cancelled/expired →                           │
     │               │    planService.revokePremium(userId)           │
     │  GET /api/v1/plan  →  "PREMIUM"  (instantly — live lookup)     │
What you'd add to this codebase (~3 files, no changes to enforcement):

p2p.billing.BillingService — holds the tier table (price/plan id → storageBytes), creates checkout sessions via the gateway's REST API (RAZORPAY_KEY_ID/KEY_SECRET or STRIPE_SECRET_KEY from env), and handles webhook events. Store the gateway's subscription_id alongside the userId (extend the Subscription record) so cancellations map back.
Two routes in ApiRouter:
POST /api/v1/billing/checkout — authenticated; embeds userId in the checkout's metadata/notes so the webhook can identify who paid.
POST /api/v1/billing/webhook — no auth, but HMAC-signature-verified (X-Razorpay-Signature / Stripe-Signature with the webhook secret), idempotent on event id. This is the only security-critical piece: without signature verification anyone could POST themselves premium.
UI: an "Upgrade" button in the Links panel's plan line → hits checkout → window.location = checkoutUrl; on return, re-fetch /api/v1/plan.
Renewals and expiry come free with your existing design: each invoice.paid/subscription.charged webhook calls grantPremium again with the new current_period_end as expiresAtEpochMs, and Subscription.active() already downgrades anyone whose period lapses — even if a cancellation webhook is missed.
